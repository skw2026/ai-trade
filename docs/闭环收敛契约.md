# 闭环收敛契约

## 1. 目的

本契约先证明“学习与晋升机制可信”，再讨论策略是否盈利。单次报告 PASS、模型 AUC
过线、服务持续运行或长期不交易，都不能单独证明闭环已经收敛。

闭环只允许按以下状态推进：

`TRAINED -> REPLAY_VALIDATED -> REGISTERED -> CANARY -> PROMOTED`

任一阶段证据不足时进入 `REJECTED` 或 `EVIDENCE_INSUFFICIENT`，不得通过放宽阈值、
更换统计口径或复用旧模型的结果继续晋级。

## 2. 单一候选身份

一轮闭环只能有一个候选身份，至少绑定：

- `git_commit`
- `model_version`
- 模型文件 SHA-256
- 训练报告 SHA-256
- replay 配置 SHA-256
- 规范化执行策略 SHA-256
- replay/runtime `trade_bot` SHA-256
- replay 报告 SHA-256
- registry entry/model version
- live runtime model version

`strategy_candidate_manifest.json` 是候选身份的权威索引。训练 A、回放 B、注册 A、
线上 C 的混用属于硬失败，不允许解释为市场波动。

`run_manifest.json` 记录 Git 来源及所有关键产物哈希。无法确定 commit 或关键产物不可
追溯时，本轮报告不得作为晋升证据。

`config/closed_loop_contract.json` 是 action 步骤和必备产物的唯一合同源。runner、
报告生成器和 GitHub Actions 必须核对同一合同 SHA-256；`full` 即使主命令退出 0，
只要缺少任一步骤或任一必备产物，也必须判定失败。

`artifact_attestation.json` 在报告和 `latest_run_meta.json` 完成后生成，独立绑定合同、
`run_manifest.json`、最终报告和 run meta 的 SHA-256 与字节数。workflow 必须重新计算
并逐项比对，避免 manifest 先生成、最终报告后变化形成未被证明的尾部产物。

## 3. 五层证据

### 3.1 P0 数据与账本

- `trade_ledger_report.json` 以 `fill_id` 去重，重复但内容冲突必须失败。
- 已实现盈亏必须从成交重建，不能由日志行数或账户权益差替代。
- 成交台账必须包含成交价盈亏和手续费；滑点只有在存在 arrival-price 基准时才能单独
  归因，资金费只有在存在真实结算事件时才能计入。
- `accounting_scope.complete_net_pnl=false` 时只允许把台账作为 fill economics 证据，
  不得把它解释为完整账户净收益或 `LIVE_VALID`。
- 无成交只能证明运行安全，不能证明交易经济性。

### 3.2 P1 离线经济性

- 模型主目标固定为
  `aggregate_model_net_bps_per_unit_turnover_after_cost`。标签可使用
  `t+latency...t+latency+h`，但净值曲线必须按实际持仓逐 bar 计一次收益。
- `execution_latency_bars >= 1`，禁止用 bar 收盘时才完整可见的特征在同一收盘价成交。
- train/test 边界必须按标签 horizon purge，并设置 embargo。
- OOS 测试窗口不得重叠；必须在原始 bar 时间轴上切分后再过滤标签，时间戳重复、
  乱序或缺 bar 均属于硬失败。
- 裁剪、归一化、Regime 阈值只能在 split train 上拟合。
- 训练报告必须声明 `training_symbol`、`bar_interval_ms`、
  `online_bar_source=closed_ohlcv`、`source_venue=bybit`、
  `source_category=linear`、`price_type=trade_price` 和
  `volume_unit=base_asset`；缺失或不一致不得注册新模型。
- live 只能消费与训练币种、周期一致的已收盘 OHLCV bar。ticker、未收盘 kline、
  其他币种行情和启动前未补齐的历史窗口都不得进入模型特征。
- 研究数据必须固定切成三个互不重叠的时间域：
  `development -> embargo -> selection-validation -> embargo -> untouched final holdout`。
  因子挖掘与模型拟合只能使用 development；候选族和参数选择只能使用
  selection-validation；最终 C++ replay 只能使用在此之前从未参与选择的 final holdout。
- Miner 的 GA 目标只能读取 development-train；development-validation 只允许输出诊断，
  不得影响适应度、排序、方向翻转或 factor-set 版本。selection-validation 冻结候选清单、
  阈值和片段边界后，final holdout 禁止 Top-N、刷新语料、追加片段或形成下一轮反馈。
- 已消费的 final holdout 只能在后续实验中作为历史 training 数据，绝不能再次进入
  selection-validation 或 final。新 selection 起点必须晚于同币种、同周期所有历史
  final 的结束时间；final 打开前必须写入持久化 append-only 消费账本。账本使用哈希链、
  tail checkpoint 和实验 ID，重复实验、区间重叠、删除或截断均硬失败。
- Python 训练特征与生产 C++ `OnlineFeatureEngine` 必须通过固定 OHLCV 黄金向量逐项比对；
  fixture 路径、内容 SHA-256、检查数量和误差上限必须同时通过 registry 门禁。
- 成本后收益不为正时，停止调参和晋升；不得用 AUC、IC 或分桶亮点豁免。
- 晋升前至少满足 OOS 换仓事件、活跃 bar、正收益 split 比例和净收益置信下界门槛。
- `backtest_walkforward.py` 的独立研究模型只作为
  `research_benchmark_only`，失败形成行动项，但不替代当前 Integrator 候选的经济门禁。

### 3.3 P2 候选回放

- replay 必须加载本轮刚训练的候选模型和特征变换，不得读取历史 active 模型。
- replay 必须使用与 live 相同的模型策略决策函数、仓位限制、成本和退出路径。
- replay 候选配置必须从本轮 runtime 配置派生；风险、执行、策略、出场、Integrator、
  自进化、Regime 与 Universe 的规范化策略哈希必须与 runtime 完全一致。专用 replay
  配置不得降低费率或放宽门槛。
- replay 的 `source_symbol` 必须等于候选 `training_symbol`，并在 manifest 中记录
  `feature_contract_match=true`；用 BTC 特征验证 SOL 模型属于硬失败。
- replay 结果必须写入候选 manifest，且候选版本与模型哈希完全一致。
- 模型注册层必须再次核对 replay 中的模型版本、模型 SHA-256 和训练报告 SHA-256。
- exact candidate 必须先用同一模型、配置、执行策略和经济目标在 selection-validation
  完整运行；其候选身份通过后才能声明并读取 final holdout。selection 与 final
  不允许只共享超参数而更换模型、二进制、成本或门槛。
- 候选身份必须包含 `economic_objective_contract_v1`：主指标固定为
  `mean_realized_net_per_fill`，并绑定成本策略、next-bar OHLC first-touch 成交、
  terminal 强制平仓成本、funding 口径、所有经济门槛以及 replay/assessor/policy
  实现 SHA-256。registry 必须重新计算全部哈希，AUC/IC 不得替代该目标。
- replay 数据耗尽后必须先撤销全部非终态订单（含 SL/TP），再强制平仓。经济分子
  必须取 `REPLAY_TERMINAL_SETTLEMENT_DONE` 中终态账户净收益，
  分母必须取当前 boot 全部 `FILL_APPLIED` 事件。最后一个 `RUNTIME_STATUS` 仅用于
  运行诊断，不得用于候选排序、成本敏感性或晋升。缺少终态结算、结算失败或成交归因
  数量不一致时，该片段必须硬失败，不得回退到旧窗口统计。
- replay 会计恒等式固定为
  `gross_pnl = realized_net + fee + funding_paid`。仅做手续费敏感性分析时 funding
  必须保持不变，场景净收益按
  `adjusted_net = gross_pnl - funding_paid - fee * fee_multiplier` 计算；
  `break_even_fee_multiplier = (gross_pnl - funding_paid) / fee`。不得把 funding
  隐含进名为 gross 的字段，也不得随手续费倍率一起缩放。
- 每个 symbol/segment replay 必须使用全新且不可复用的 `system.data_path`，禁止恢复
  live WAL、前一片段 WAL 或重试残留 WAL；状态目录已存在时直接失败，不能清空后继续。
- 独立 C++ replay 使用下一根 bar 才允许成交、maker 限价需后续 OHLC 触价的保守模型，
  只具有候选离线预筛权；它不能单独提交生产模型，最终晋升权威仅来自 live candidate
  episode canary。

### 3.4 P3 Canary

- `shadow` 只观测，不产生仓位。
- `canary` 可在明确配置后从 flat 产生小额独立模型信号；额度必须有硬上限。
- `active` 不得因基线信号为 flat 而隐式创造未经 canary 验证的新仓位。
- canary 必须按同一
  `decision_id/candidate_id/model_version/client_order_id/position_episode_id`
  依次产生 `proposed -> risk_accepted -> enqueued -> filled -> episode_closed`，
  且 episode 从 flat 开始、回到 flat、费用后净收益可重建，才形成在线经济证据。
- baseline 不得在未闭合的同币种 canary episode 中新增 entry；最终平仓必须把
  `EPISODE_CLOSED4` 写入 WAL，重启恢复按 episode ID 补发和去重证据。WAL 记录必须
  原子固化策略原因、费用后净收益、估算资金成本、部署 transaction/boot/config/binary
  身份与闭合时间；旧协议只允许恢复，不得成为新候选的权威晋升证据。
- 只有 `policy_reason=canary_independent_signal` 的独立模型开平仓 episode 才能证明模型
  增量经济性；与 baseline 同向的缩放/对齐仓位、重启恢复补录和身份不完整的 episode
  一律不进入晋升样本。
- 行情资金费率按事件时间折算后可作为保守经济成本进入候选 episode，但它仍是
  `prorated_indicative` 估算，不是交易所结算流水。没有真实 funding transaction 和
  arrival-price 滑点前，报告不得把该口径升级为完整账户净收益。
- `full` 只能把新模型放入 `canary_pending_evidence`，不能因技术步骤退出 0 直接提交。
  transaction 状态和旧 active 四件套备份必须存放在 `data/models`，不得依赖会被 GC
  清理的单次 run 目录。
- 后续 `assess` 按 `position_episode_id` 跨窗口累积同一候选的完整 episode。默认至少
  30 个 episode、正收益比例不低于 50%，并按 episode 先计算
  `realized_net_usd/fill_event_count`；该分布的 Student-t 95% 置信区间下界必须严格
  大于净收益门槛。model/report/runtime-config/trade-bot 四段身份和 feature contract
  也必须完全一致，才允许 `commit`。
- 达到最小样本后经济门禁失败、候选身份漂移、出现其他候选成交、active 产物被修改，
  或出现硬安全事件时必须恢复旧 active 四件套并验证旧进程身份；任何 pending 条件
  （包括 episode 不足、runtime verdict 不可提交或身份证据不完整）持续 72 小时仍未解决
  也必须回滚。未超时只保持 pending，不得伪装为失败或成功。
- pending 期间禁止第二个 `full` 覆盖候选；runner 必须持有进程锁，避免 scheduler 与
  GitHub Actions 并发修改 transaction。
- 只有通用成交、只有模型提案或只有入队而没有候选归因成交，都属于
  `EVIDENCE_INSUFFICIENT`，不是 PASS。

### 3.5 P4 在线自适应

- 反事实候选只用窗口前段选择，后段时间 holdout 独立验收。
- holdout 样本不足时输出 `EVOLUTION_COUNTERFACTUAL_HOLDOUT_INSUFFICIENT` 并冻结更新。
- 严格时间 holdout 模式禁止退回全窗口原位选优或 factor-IC 旁路。
- 成本过滤率不能降低候选改进门槛。
- Sharpe-like 分母必须有现实风险下限，禁止零回撤导致目标函数爆炸。

### 3.6 P5 发布事务

- 构建产物必须以镜像 digest 和候选 manifest 绑定；部署前重新计算配置与二进制哈希，
  禁止以可变 tag 或工作目录当前状态替代本轮候选。
- CD 必须持有部署锁，先启动核心交易服务并验证四段身份，再启动 watchdog/scheduler；
  任一阶段失败均恢复上一不可变镜像 digest 和旧 active 四件套。
- 回滚成功必须重新验证旧容器健康与身份；“已执行 rollback 命令”不等于回滚成功。
- scheduler、手工 workflow 和 CD gate 不得并发写 active transaction。生产编排不得
  暴露 runner 已不再消费的环境变量，避免形成伪配置控制面。
- CD、workflow 和 scheduler 只能从 `releases/<git_sha>` 不可变目录执行，并同时核对
  release manifest、内容清单、runner SHA-256 与运行镜像 revision。runner 自身必须有
  独立于 SSH 的硬截止时间，超时/信号/非零退出统一回滚本轮 transaction。
- scheduler 默认只执行 `assess`，不得周期性执行 `full` 消耗 final holdout；每次任务
  持久化 running/sleeping/failed 状态，失败或超时必须使容器 health 失败并由 watchdog
  告警。

## 4. 硬停止条件

满足任一条件即停止本轮优化，不再继续微调：

- 候选身份不一致或关键产物缺失。
- holdout 成本后期望不为正。
- replay 未加载当前候选。
- replay 仅靠不交易通过。
- canary 没有模型 applied/fill 证据。
- 交易账本存在冲突成交或无法重建。
- 线上触发硬风控、对账异常或不可恢复数据异常。

停止后必须先修证据链或更换 alpha/频率/标签。禁止通过降低费用假设、减少最小样本、
放宽显著性或只选有利币对，把失败改写成通过。

## 5. 晋升判定

机制证明和盈利证明分开：

- `MECHANISM_VALID`：候选身份一致、无泄漏回放、门禁可阻断、canary 可产生受限动作、
  回滚可执行。
- `ECONOMICS_VALID`：独立 holdout 与 replay 在真实成本后为正，且不是少数片段贡献。
- `LIVE_VALID`：canary 的真实去重成交达到预设样本量，净每笔、回撤和成本均过线。
- `PROMOTED`：前三项全部成立，且没有 KRI 一票否决。

机制未证明前，不允许以“再跑 12/24 小时”代替工程验证。只有 replay 已通过且 canary
已实际生效后，12/24 小时 soak 才用于积累 `LIVE_VALID` 证据。

## 6. 本轮实现边界

截至 2026-07-27，仓库已实现：

- Git/产物哈希追溯与统一成交账本。
- walk-forward 非重叠经济曲线、purge/embargo、split-train 特征变换。
- 训练/replay/live 单币种已收盘 OHLCV 特征契约、生产启动历史 bootstrap、
  错币种/错周期/特征过期自动禁用模型。
- 当前候选专用 replay 配置与 `strategy_candidate_manifest.json`。
- replay/runtime 规范化执行策略和 `trade_bot` 二进制身份绑定。
- 数据管线显式区分 required 数据产物与 diagnostic-only 研究 benchmark。
- 研究数据固定为 development、selection-validation、untouched final holdout 三个隔离
  时间域，两个边界均有 embargo；registry 会重新核对各域文件哈希和实际消费者。
- Python 训练语义与生产 C++ 在线特征引擎使用不可变黄金向量做逐项 parity 检验；
  fixture 路径、SHA-256、覆盖数或误差任一不符都会阻断注册。
- C++ replay 的 maker 与条件退出均采用下一 bar 之后的 OHLC 触价成交，只作为保守
  离线预筛；生产提交必须等待 live candidate episode 的统计证据。
- `full` 在 runtime 验收前加载本轮候选，避免拿旧模型运行证据证明新候选。
- `full` 不在技术步骤通过后直接提交候选；新候选进入持久化
  `canary_pending_evidence`，后续 `assess` 以 episode 数而非固定等待时长裁决。
- canary 独立小额模型提案，复用 live 模型策略函数。
- WAL 恢复后的订单/成交归因、候选 episode 闭合确认，以及远端遗留仓位 SL 重建门禁。
- 持久化两阶段激活 transaction：`full` 只 stage，`assess` 跨窗口累计 episode 后自动
  commit/rollback；身份漂移、负经济性、超时和硬安全事件均 fail-closed。
- active 模型、报告、miner 报告和 active meta 的事务快照/恢复，以及恢复后旧模型
  runtime 身份验证；无可恢复旧版本时停止交易服务。
- runner 互斥锁、同一 pending 候选期间禁止再次 `full`，并输出
  `activation_transaction.json` / `activation_decision.json` 供 workflow 下载。
- 自进化严格时间 holdout 和稳定风险分母。
- Miner 的验证集不参与 GA 选择、方向翻转与版本生成；selection manifest 在 final
  holdout 打开前冻结，final holdout 不再反馈候选搜索。
- exact Integrator 候选先在 selection-validation 完整回放，同一候选身份再进入 final；
  经济目标契约将净每笔、执行成本、成交/终止/funding 语义、阈值和实现哈希统一绑定。
- final holdout 使用持久化哈希链账本和 checkpoint 在评估前声明消费；历史 final 只能
  作为后续历史训练，不能再进入 selection 或 final。
- canary episode 使用部署 transaction、boot、runtime config 和 trade-bot 四段运行身份，
  仅独立模型信号形成权威证据；闭合经济数据以 `EPISODE_CLOSED4` 原子写 WAL。
- 手续费、成交盈亏和按事件区间折算的 indicative funding 已进入统一经济账本；报告
  明确保留“尚无真实 funding settlement/arrival-price”边界。
- CD 使用不可变镜像 digest、`releases/<git_sha>` 内容清单、部署互斥锁和经身份复验的
  事务回滚；runner 有 80 分钟内部 deadline，scheduler 默认 assess 并暴露持久化健康状态。

仍需由真实运行证据完成的项目：

- 当前候选 replay 的成本后稳健正收益。
- canary 的模型 applied、真实 fills 与净收益样本。
- live 真实资金费结算流水与 arrival-price 滑点归因，完成账户净收益对账。
- 更大样本下对 canary 自动提交阈值和 72 小时证据截止线的真实运行校准。
