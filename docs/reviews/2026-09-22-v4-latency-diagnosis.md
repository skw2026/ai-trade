## 为什么不能再靠重跑收口

当前聚合审计只要出现一个无效段就 FAIL；它吞掉具体异常，只留下数量。若原件确认超时，增加正常分段不会使这个历史分段重新满足时间合同，内存修复也不能逆转过去的观测耗时。不得删除分段、改历史时间、提高 120 秒阈值或等待保留策略清掉它来换取 PASS。

当前工程发布检查又绑定持续增长的研究归档，因此“固定部署实现是否正确”和“所有后续采集是否始终无缺陷”耦合。上一批已关闭候选的生命周期字段没有变化，仍可被另一个分段阻断。这里只确认该结构性依赖；不自动把它从验收中去掉。

后续原件确认后仍有两个明确出口：保留原验收则本批继续如实 FAIL，不无依据重试；若用户选择将固定工程回归/关闭锁存检查与动态数据质量分别裁决，另行冻结新边界，质量 FAIL 和禁止晋级继续保留，不把旧整批失败追溯改为成功。后者属于实质验收决策，当前尚未实施。

## 为免继续人工搬运而准备的最小入口

新增本地 `tools/diagnose_option_lifecycle_segment.py`，仅核对一个名称、报告哈希和当前 release 都指定的分段：

1. 核对冻结策略、报告 SHA256、关联 raw/features 路径和校验和。
2. 有界逐行读取该段压缩原件，报告原件最大耗时、超时行号、起止时间、报告计数/最大耗时是否与原件一致。
3. 只输出名称、哈希、计数、时间与固定原因码；不输出行情、账户、异常原文。退出 0 只代表取证完成，不能代表分段合格或工程验收通过；其他快照合同、跨段关系明确未验证。

配套 `.github/workflows/ecs-segment-diagnostic.yml` **仅本地草稿，未提交、未发布、未执行**：仅手动 dispatch，沿用既有可信指纹 SSH；脚本经 stdin 执行，不上传脚本或写 ECS 文件，不触发 CD、不改 release、不调用交易/研究接口。job 上限 5 分钟，远端程序 90 秒、512 MiB 地址空间；只保留脱敏回执，SSH 原始输出不上传。

本地 12 个小型离线诊断样例通过，覆盖时间边界、原件哈希不符、元数据不一致、目录穿越、符号链接、读取/解压上限、release 不符、错误脱敏及输入不变性；YAML/内嵌 Python 静态检查通过。均不是正式 gate retry 或 ECS 验收，未接入 CTest 计数，不宣称远端已可用。

已向用户提出一个明确的**流程例外决策**：BLOCKED 时允许发布/执行有界的诊断专用工作流，但仍禁止交易服务部署、正式验收重跑和门禁放行。现行协议禁止失败后继续发布，因此在答复前不自行 push。该问题不是重复索要普通代码发布权，也不申请提高数据阈值。

工程 gate 保持 BLOCKED、failure_count=2；旧研究保持 HALTED；原接受复盘和原失败记录不改。详细来源、合成边界与门禁哈希见[机器记录](2026-09-22-v4-latency-diagnosis.evidence.json)。
