## 为什么严格回退不能靠删除一行修绿

生产`SelfEvolutionController::OnTick`明确要求非严格模式才进入
`ShouldRollback`分支。原普通模式回滚测试不覆盖严格模式；本次真实模型的
三个负窗也没有该回滚。严格模式还会在“不足/无相对改善”等条件提前返回，
部分情况下根本到不了退化计数。

现有方法是统计候选替换：训练段选更好的权重，留出通过才应用。
它不是独立安全撤回：即使所有权重都亏损，也可能选到相对少亏的权重。
直接恢复旧基线不一定降风险：当前趋势权重0.40时恢复0.50会增加趋势敞口；
“旧模型/旧权重”也不能自动视为当前留出合格。

因此本批不能擅自删严格保护、开factor-IC旁路、恢复旧候选、改变账户风控，
也不能用回归全绿宣称完整自学习闭环完成。

## 收口复盘与下一项实质选择

这是内部工程/统计/风险多视角复核，不冒称外部专家圆桌。

- 工程根因：此前组合驱动没有给控制器输入真实模型策略信号，严格分支与
  普通反馈分支分开测试，漏掉可达候选与回退动作的组合约束。现在已直接复现
  并限定修复步长问题，不再用组件数量或部署成功替代这一证据。
- 统计根因：总收益上涨包含可变仓位；严格候选相对改善也不等于绝对经济资格。
  配对名义本金对照已把这两种含义拆开，未寻求新种子/新参数“重新做正”。
- 产品根因：统计调权与安全撤回混为“回滚”，但严格模式故意禁止未经验证
  的权重恢复，尚无与这条约束兼容、接到执行边界的独立退化处置合同。
- 执行教训：固定范围应包含行为模式和可执行验收项，不能每交付一个技术
  子批次就把整个剩余主线简化成“只缺市场资格”。Linux容量问题是本次验证
  环境与旧单测的依赖错误，已单独定位；不把它当成新的研究方向或无限修复入口。

   不能重启即解锁。下一验收必须覆盖控制器→策略/执行边界→持久化→重启，

2. **仅统计回退。** 旧权重先经同样严格留出验证，合格才恢复；证据不足只冻结
   调权，不承诺候选停止新增风险。这与方案1的风险语义不同。
