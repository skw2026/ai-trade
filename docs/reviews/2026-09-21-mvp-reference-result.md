## 1. 这次真正消除了什么阻断

上次最早失败点是“离线假想持仓没有逐仓资本模型”，而不是公共行情不存在。此次增加显式 opt-in `replay_reference_account`，独立维护参考抵押余额、已成交数量、加权成本、funding 和资金占用，向风险决策提供带 `RISK_OFFLINE_REFERENCE_MARGIN_V1` 来源的参考距离。

2x、1% 维持率、13bps 退出负债预留、单档位和精度均为预先冻结的参考假设，不是 Bybit 实际/历史账户参数，也不保证在所有路径上偏保守。官方资料仅用于确认逐仓、mark 和保证金的概念结构：[Bybit 逐仓/强平](https://www.bybit.com/en/help-center/article/UTA-Trading-Rules-Liquidation-Process)、[初始保证金](https://www.bybit.com/en/help-center/article/Initial-Margin-USDT-Contract)。本合同的资产负债等式不冒充官方完整算法。

## 3. 两次失败如何暂停、分析、复验

两次是不同验收中的独立问题，均在失败后暂停依赖步骤，保留证据，根因确认后原命令仅复验一次；不是同一未知原因反复重跑。

1. **新增 gross 校验的估值口径错误。** 首次参考账户测试在第三次追加订单第二个 partial 被拒绝：数量 5.952，mark 504 对应 gross 2999.808；新实现却用 `max(mark, fill)` 的 504.1 重估全部旧仓，得到 3000.4032。修复为 gross 用 mark，保证金及费用仍用实际 fill，3,000 限额和原用例不变。原 CTest 复验通过。[完整复盘](2026-09-21-mvp-reference-gross-review.json)，原始失败日志保留在 `.artifacts/mvp-reference-20260921/first-account-failure.log`。
2. **压力成本用例的预期错误。** 原组合用例产生约 20bps 合成信号，基础场景有 1152 个成交部分，压力场景因 27bps 费用门槛正确过滤。错误是测试假定两者都应成交，不是整条 CLI 链路零成交。保留原 slope=1 输入为费用拒绝负例，另加预先按 `2/500=40bps > 27bps` 指定的人工执行正例；不改策略/成本/合同，不要求合成经济裁决为正。原 Python 命令复验 25/25，通过后继续扩至最终 29 项。[完整复盘](2026-09-21-mvp-reference-cost-fixture-review.json)，原诊断输入、两日志、plan/result 留在 `cli-zero-fill-inputs/` 与 `cli-zero-fill-reproduction/`，其旧二进制身份不冒充最终版本。

第一项也暴露了门禁工具缺少“已审核的源码修复需先重建”入口。此次只增加受复盘哈希、原 cwd、精确 `cmake --build` argv 约束的一次 `repair-build`；构建通过仍保持 RETRY_APPROVED，不是 READY，仍须原测试复验。构建失败重新阻断、累计失败次数；14 项门禁测试覆盖拒绝绕过，协议同步更新。未删除状态、另换 state 或裸重跑测试绕过门禁。

此外，收尾代码检查补齐末端手续费后的风险更新和运行后身份校验；随后定向及全量验收通过。不能用本次修复证明未来不会再有问题，只能证明本矩阵的工程条件已有明确证据。
