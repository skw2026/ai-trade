# 固定工程回归与动态数据质量分开验收

## 用户方向与旧阶段处置

上一轮已明确建议将固定工程回归与持续数据质量分别裁决，保留数据 FAIL，并说明属于验收边界变化。用户随后回复“继续”。本轮据此实施该具体建议，不再次请求逐步确认，不把它扩大为盈利研究、实盘或历史标准修改。

旧 `.artifacts/engineering-freeze-20260921/validation-state.json` 以有证据的 `decision=stop` 进入 HALTED，保留 failure_count=2、原命令和所有失败。原 observe.py 不改，不用 retry 把旧验收改绿。旧研究 HALTED 不变。

新阶段状态独立为 `.artifacts/engineering-boundary-v1-20260922/validation-state.json`：这是用户接续明确边界建议后的新阶段，接受标准变化显式记录，不是暗换状态文件绕过旧失败。门禁程序本身不改。

## 在执行前固定的出口

| 对象 | 必需条件 | 不代表什么 |
| --- | --- | --- |
| 工程交付 | 精确 main SHA 的 Linux CI、Docker/CD、Smoke 全部真实通过；固定回归工作流通过 | 不代表盈利、所有动态采集合格或实际策略接管 |
| 固定回归 | 同一冻结 120 秒合同的边界接受/超时拒绝；原始负例结果 INVALID 不变；六期 STOP 锚点哈希/契约/账务复核，候选保持 CLOSED | 不拿旧锚点冒充本轮新行情、账户账单或新经济结果 |
| 动态数据质量 | 原 Archive、V4 工作流仍执行，保留原退出语义和数据裁决；完整记录报告和精确 release 身份 | FAIL 不转 PASS，不通过 continue-on-error 伪装工作流成功 |
| 发布收据 | 同时输出 engineering 与 data_quality；当前已知 V4 超时为 FAIL，Archive 为证据不足；总业务不合格和权限 false | 不输出“所有检查通过”或给予激活权限 |

工程成功的同时必须明确呈现数据 FAIL/INSUFFICIENT。动态审计若缺真实报告、release 身份错、出现未知执行错误或新增未解释的故障，不以“已拆分”为由忽略。已知时效负例按本计划事前声明，不作为工程回归的意外失败；其原始 V4 workflow 仍应 failure。

固定关闭检查从旧工具提取同一套 anchor 验证，不降低 ZIP 哈希、三报告交叉身份、冻结经济合同、原始六期账务、STOP 条件和无权限约束；新增 anchor-only 出口必须明确 current/live 未评估，原带 --current 路径保持严格。

新增分段拒绝诊断必须只增加可观测字段，不改变归档校验、快照选择、时间阈值或权限。只输出受限文件身份/哈希/固定原因码，避免再次需要手工提供主机日志。已有单分段工具接入 CI 回归。

## 顺序、预算与停止条件

1. 确认旧失败停止、新边界与机器判定合同。实现限一个批次、90 个有效工程分钟；不采新行情、不重算新策略、不动旧合同原件。
2. 新阶段正式本地 configure/build/test 通过门禁；定向负例、完整 CTest、固定真实锚点核对后，直接 main 一次发布。仅使用既有 Demo 测试环境 CI/CD，不改策略/风控配置。
3. 观察精确 SHA 的 CI/CD、Smoke、固定回归与原数据工作流；必须取得数据失败原因和部署身份，不把诊断任务成功或 skipped 当验收成功。现有任务超时上限保持，普通构建等待由执行者跟踪。
4. 若工程通过但数据不合格，按本边界结案并记录两种结果；不等待两周、不重开候选。任一未预期失败先分析，只有证据与路线支持才按原命令一次复验；不加预算或盲重跑。

历史超时不得删除、挪出审计输入、改时间或提高阈值。新阶段通过不修改旧阶段 HALTED、研究 HALTED、C2 NOT_QUALIFIED、NO_QUALIFIED_CANDIDATE。
